# AgentNodify

## 仕様

CodexやOpenCodeのようなチャット型エージェントをノードとしてワークフローを定義し、自由にタスクを処理させることができる。

### 概念

- フロー: 処理の流れ。定義したフローはファイルとして保存できる。
- ノード: フローの中の単位要素。互いに入出力を繋げて順序を定義することができる。一部の例外を除き、基本的には任意個数の出力とただ一つの入力を持つ。
- プロジェクト: フローによって処理される作業の単位。一つの何らかのディレクトリに対応。

### 実行ルール（追加）

- ループを許可する。通常ノードは前段ノードから発火されるたびに再実行する。
- 同じ入力ポートに初回の入力辺とループの戻り辺など、複数の辺を接続できる。
- ANDノードは全入力の発火を待って1回実行し、消費済み入力の状態をリセットして再び全入力を待つ。
- 実行中や待ち合わせ中に到着した追加の入力はFIFOで保持し、次の実行／待ち合わせに使用する。
- 分岐の非選択出力は発火しない。非選択入力をANDノードの入力完了とはみなさない。
- 各CLIの作業ディレクトリは選択したプロジェクトとする。作業ディレクトリ・CLI出力をログで確認できる。
    - プロジェクトを絶対・正規化パスに解決し、子プロセスのカレントディレクトリと`PWD`を一致させる。Codexには`--cd`でも同じ場所を明示する。
    - OpenCodeのタスク実行は常に`--standalone`で専用サーバーを使い、既存の共有サービスのプロセス・作業場所に依存しない。ユーザーの共有サービスを停止・変更はしない。権限バイパスのオプションも追加しない。
- CLI設定の「プロジェクトへの書き込みを許可」は初期状態で無効。明示的に有効にした場合のみCodexに`--sandbox workspace-write`、Claude Codeに`--permission-mode acceptEdits`を渡す。denyルールは維持し、全権限のバイパスはしない。Claude CodeのacceptEditsはOSサンドボックスではない。OpenCodeの権限は既存CLI設定を使用する。
- CLIの正常終了はタスク達成・ファイル作成を保証しない。権限拒否も各ノードのログ・出力で確認する。

#### ノードの種類

- 始端ノード/終端ノード: 処理の始まりと終わりを表し、1つのフローにそれぞれただ1つずつ存在する。
- エージェントノード: チャット型エージェントに投げる1タスクに対応する。
    - エージェント: 使用するエージェント。Codex/Claude Code/OpenCodeを選択可能。
    - モデル: 使用するモデル。指定したエージェントから利用可能な候補一覧を自動取得して選択できる。
        - 起動時、エージェント切替時、モデル選択欄を開く際に非同期で取得する。取得中も画面操作を妨げない。
        - Codexはapp-serverの`model/list`（ページ送り対応）、Claude Codeは制御プロトコルの初期化応答の`models`、OpenCodeはCLIの`models`コマンドを利用する。
        - 一覧取得のためのプロンプトや推論リクエストは送信せず、CLI設定・認証を利用する。認証情報のコピーや自動ログインは行わない。
        - 取得結果を10分間メモリにキャッシュし、複数ノードからの同時要求をまとめる。取得失敗後は30秒間、自動再試行を抑制する。
        - ノード内のモデル欄の更新ボタン、またはツールメニューから、キャッシュ期間に関係なく再取得できる。
        - CLI設定を変更した場合は、変更された実行ファイルのキャッシュを無効化して再取得する。
        - 取得失敗・タイムアウトの場合は状態を表示し、前回の候補があれば保持する。固定の推測モデル一覧には置き換えない。
        - モデル欄は純粋な選択式とし、手入力と「CLI既定」の選択肢を設けない。未選択ではプレースホルダーを表示し、アプリからの検証・実行前に選択を促す。
        - 既存ファイルで設定済みのモデルIDが一覧外にあっても「現在の設定」として保持する。一覧更新だけでフロー定義を変更しない。
        - 一覧はCLIが返す候補であり、課金・アカウント権限・プロジェクト固有設定による実行可否まで保証するものではない。
        - 候補と選択値はモデル名のみ表示し、IDは内部データとツールチップに保持する。
        - Windowsの旧初期設定`opencode`だけを`opencode-cli`へ移行する。手動指定の実行ファイルパスは変更しない。
    - 思考量: 未指定はCLI・モデルの既定値。モデル一覧が対応レベルを返す場合はその候補を使い、情報がなければ一般的な候補を表示する（モデルの対応は保証しない）。Codexは`model_reasoning_effort`、Claude Codeは`--effort`、OpenCodeは`provider/model#variant`で指定する。OpenCodeで思考量を指定する場合はモデル指定が必要。
    - 入力プロンプト: 入力するプロンプト。複数行入力可。固定の文字列のほか、前段の出力内容を`${変数名}`の形式で利用することもできる。前段のスキーマに存在しない変数名の場合はエラー。
        - 例1: 前段が`{"a": "b"}`を出力したとき、入力プロンプト内で`${a}`とすると`b`という値で置き換えられる。
        - 例2: 前段が`{"hoge": {"foo": "bar"}}`を出力したとき、入力プロンプト内で`${hoge.foo}`とすると`bar`という値で置き換えられる。
        - 例3: 前段が`{"foobar": ["baz", "qux"]}`を出力したとき、入力プロンプト内で`${foobar[1]}`とすると`qux`という値で置き換えられる。
    - 出力スキーマ(任意): 出力応答のスキーマ。複数行入力可。JSON Schemaを指定することができる。指定するとStructured Outputを行うことができる。指定しない場合は普通のテキスト出力になる。JSON Schema定義が正常なJSON Schema定義になっていない場合はエラー。
- ANDノード: 複数のノードの結果終了を待つノード。任意個数のノードの出力辺を入力に繋げることができ、フロー実行時にはすべてのノードの終了を待つ。
    - 接続した入力ノードは0-indexedで番号が割り振られ、出力は対応した配列になる。
        - 例: 入力0のノードが`{"a": "b"}`, 入力1のノードが`{"c": "d"}`を出力したとき、ANDノードは出力として`[{"a": "b"}, {"c": "d"}]`を出力として次段に伝播する。
- 分岐ノード: 前段の出力内容に応じてフローの伝播先を変更する。
    - 条件: 任意の個数を指定できる。if-elseif-else型のルールで評価され、一番最初に真になったものが採用される。
    - 条件変数: 前段の変数名。前段のスキーマに存在しない変数名の場合はエラー。
    - 条件値: 条件変数と比較する値。任意の文字列が指定できる。
    - 条件: 条件変数と条件値の比較方法。「等しい」「異なる」から選べる。
    - 条件UIは「条件1」「もしも [変数名] が」「[値] と [等しい/異なる] ならば」の3段。出力ポートは「条件1」等と「それ以外」を表示する。

### 画面

- メインウィンドウがある。
    - ファイルメニューは名前とショートカットが詰まらない項目余白を持つ。固定の最小幅は設定せず、文字列に応じた自然な幅とし、項目の右側に大きな未使用領域を残さない。
- メインウィンドウの左端には、Slackのワークスペース一覧を参考にした縦型のフロー一覧バーがある。
    - 定義済みフローと+ボタンを同じ枠内に並べる。
    - 各フローボタンと+ボタンは、同じ大きさの角丸正方形とする。
    - フローボタンには名前の略称を表示し、ツールチップで完全な名前を確認できる。
    - ボタンにはホバーエフェクトを付け、選択中のフローは枠線・背景色で区別する。
    - +ボタンでメニューを開き、「新規フロー」「既存フローの追加」を選ぶ。
    - フローの右クリックメニューに「名前を変更」「一覧から削除」を設ける。ファイルメニューにはフロー名変更を置かない。
    - アプリ内部のAppData/flowsにしか保存されていないフローは、警告・確認後に定義データも削除する（未保存の定義も破棄する）。外部保存フローは一覧からのみ除去しファイルを変更・削除しない。未保存の外部変更があれば破棄を追加確認する。
    - 左上の「AN」等のブランド表示は設けない。
- メインウィンドウ内部には2つのタブがある。
    - フロー編集画面
    - プロジェクト作業画面

#### フロー編集画面

ノードベースの編集UIがある。横割れ2ペインもしくは3ペイン。境界はドラッグ移動可。

- 左側にノードを選べるペインがある。
    - 選べるノードが縦に並んでいる。
    - クリックするとノードが追加できる。
    - ノードのパラメータ編集フォームや「接続を追加」ボタンは置かない。
    - ノード追加ボタンにカーソルを一定時間当てると、ノードの機能説明をツールチップで表示する。
- 中央にノード編集UIがある。
    - 各ノードの接続・移動・パラメータ編集ができる。
    - パラメータの編集フォームは、左ペインではなく各ノードの図形内に表示する。
    - 選択式ボックスの候補リストもダークテーマに合わせ、明るい文字と暗い背景で表示する。選択・ホバー時にも文字のコントラストを維持する。
    - 選択式入力と候補リスト上のカーソルは通常の矢印にする。ノード画面のパン操作用の手形カーソルを継承しない。
    - フォームや候補リスト上のホイールは埋め込みウィジェットへ配送し、リストのスクロールを優先する。リストの先頭・末尾でもノード画面を拡縮しない。背景上のホイールによる拡縮は維持する。
    - 名前、エージェント、モデル、AND入力ポート数、分岐条件の変数・比較方法・値はノード内で編集する。
    - 分岐条件の追加・削除もノード内で行う。
    - プロンプト・出力スキーマなどの複数行パラメータは、ノード内に複数行のプレビューテキストボックスを表示する。
        - クリックすると、対応するパラメータの編集UIを右ペインに表示する。
        - ノード内のプレビューは読み取り専用とし、右ペインの編集内容を即時に同期する。
        - 改行と折り返しに応じて高さを自動的に伸縮し、表示行数は最小1行・最大8行とする。テーマの余白を含めて高さを計算し、8行以下ではスクロールバーを出さない。8行を超える内容はスクロールして確認できる。
    - ノードの図形にも、長時間のホバーで機能説明のツールチップを表示する。機能説明はフォーム下部等に常時表示しない。
    - 内部のノードIDは保存・接続の識別にのみ用い、タイトル、フォーム、接続ダイアログ、エラーメッセージにはユーザー向けの連番として表示しない。
      ANDの入力ポート番号など、入出力の意味を示す番号は引き続き表示する。
    - 始端・終端は特別な黄色背景のノードとし、「始端」「終端」だけを1行で表示する。
      タイトルとポートラベルを重複表示して「始端 出力」「終端 入力」の2行にしない。
    - 接続はポートのドラッグで行う。ツールメニューの「接続を追加」は設けない。ループの実行・保存形式のサポートは維持する。
    - ノード本体の右クリックメニューに「削除」を表示する。ノードと接続辺をまとめて削除し、右ペインの選択も解除する。始端・終端は削除不可、実行中も削除不可とする。
- 右側にテキスト編集UIペインがある。ノード内の複数行テキストボックスを選択したときのみ出現。
    - 簡易なシンタックスハイライトが行われる。
    - 別ノードや単一行パラメータを選択した場合、または閉じるボタンを押した場合は非表示にする。

#### プロジェクト作業画面

横割れ3ペイン。境界はドラッグ移動可。

- 左側にプロジェクト一覧ペインがある。
    - プロジェクトのリストが縦に並んでいる。クリックすると選択することができる。
    - 各項目の右側にゴミ箱アイコンを置き、一覧から削除する。単独の削除ボタンは設けず、プロジェクトのディレクトリ自体は削除しない。
    - ゴミ箱の左に「…」ボタンを置き、クリック時に検出済みアプリだけのメニューを表示する。候補は「エクスプローラーで開く」「コマンドプロンプトで開く」「PowerShellで開く」「Git Bashで開く」「VS Codeで開く」「VS Code Insidersで開く」。
        - PATH、Windowsの登録情報、標準インストール場所から実在するネイティブ実行ファイルを検出する。VS CodeのPATH上の.cmdからも本体.exeを特定する。検出だけで外部アプリを起動しない。
        - 選択時に対象プロジェクトを作業ディレクトリとして起動し、ファイルマネージャー・エディター等にはパスを独立した引数で渡す。シェル文字列にパスを埋め込まず、検出・起動失敗時も他アプリへの勝手なフォールバックはしない。
- 中央にプロジェクトのフロー表示がある。
    - 右上に実行ボタンがあり、クリックするとフローの実行がトリガされる。
    - ノードベースの形で現在のフローの実行状態が表示される。
    - 現在実行中のエージェントノードは実行中らしいアニメーションアイコンが表示される。
    - ノードをクリックするとそのノードを選択できる。
    - 編集画面と同じノード内フォーム・配置を表示する。ただし移動・接続変更・パラメータ編集はできず、選択はできる。フォーム内のクリックでも右ペインを更新する。
- 右側に選択したノードの情報が表示される。状態表示の下は、縦方向のスプリッターで「実行履歴」「進行状況 / CLIログ」「次段への出力」の3分割にし、各領域の高さを変更できる。
    - 実行履歴は**ノードの実行1回ごと**に記録する。ループ中の再実行も別の履歴とし、フロー実行ごとにはグループ分けしない。
    - 各行に開始日時（ローカル時刻・ミリ秒）、状態、実行時点のノード名を表示し、新しい実行順に並べる。ノードを選択するとそのノードだけの履歴、未選択時はプロジェクト内すべてのノードの履歴を表示する。
    - 履歴を選択すると、その1回の状態・CLIログ・次段への出力だけを表示する。再実行で以前の回のログや出力を上書き・混在させない。
    - 「最新を追従」が有効なら最新の実行に自動追従する。履歴を選択すると追従を停止し、新しいノード実行やログ更新があっても選択した過去の回を維持する。ノードの選び直し、または追従ボタンで最新表示に戻せる。
    - 成功・エラー・中止を記録し、まだ実行されていない待機／スキップだけのノードは履歴を作らない。開始・終了日時を保持する。
    - 起動時にノード未選択なら最初の実行中エージェントノードを自動表示する。ログ更新時、末尾を表示中なら追従し、過去のログを閲覧中ならスクロール位置を保つ。UTF-8がチャンク境界で分割されても文字を維持する。

#### 実行履歴の保存

- アプリのAppDataLocation配下の`history/<プロジェクトの登録ID>/<ノード実行UUID>.json`に保存する。ワークスペースにプロジェクトの登録IDを保持し、アプリの再起動・フローの再実行でも履歴を復元する。プロジェクトの作業ディレクトリには履歴ファイルを作らない。
- 実行開始・終了時は直ちに、実行中のログは約1秒ごとに現在の記録をアトミック保存する。終了時も未保存分を保存し、保存できない場合は警告する。履歴自体は自動削除しない。ログは既存の1実行あたり約2Mi文字の保持上限を引き継ぐ。
- 正常終了を確認できずに保存された「実行中」の記録は、再起動時に「中止（中断）」として表示する。分からない終了日時は補完しない。壊れた記録は報告してスキップし、他の履歴は読み込む。
- ノードを削除・追加しても以前の履歴と別ノードを混同しないよう、フローに任意フィールド`nextNodeId`を保存してノードIDを再利用しない。既存形式は読み込み時に現在の最大IDから補完する。
- CLI出力を含むローカルの平文JSONであり、機密情報を含む可能性がある。履歴ディレクトリを不用意に共有・配布しない。

## 使用予定技術

- Qt: GUIに使用, C:/Qt下にインストール済み
- QtNode: ノード編集UIに使用
- nlohmann-json: JSONの解析に使用。

## テスト

- Codex/Claude Code/OpenCodeを用いて簡単なフローを定義して動作をテスト。
- フロー定義内容にエラーがある場合のエラー検出もテストする。
- ループがある場合の挙動もテストする。
- ノード内フォームの編集、右ペインとの同期、複数行欄の1〜8行の伸縮をテストする。
- ノードの機能説明のツールチップ、始端・終端の1行表示と黄色背景、ユーザー向け連番の非表示を確認する。
- フロー一覧の同一枠内の角丸正方形ボタン、ホバー効果、フロー追加・選択を確認する。
- 各エージェントのモデル一覧取得、ページ送り、重複・非表示モデル、キャッシュ、失敗・タイムアウト、設定値を保持した候補更新をテストする。
- 以下のモデルの使用を許可する。
    - GPT-6.0-Luna
    - Haiku 5.5
